# Exclusive Apparel: waiting-list launch

This release is a price-free collection preview, not an open store. The seven photographed products remain visible. Visitors can join the waiting list without an account. Purchases, payment initiation, customer signups and the old commerce-management APIs are blocked in pre-launch mode. The supplied product images and logo remain in the repository.

## Deploy yourself

Changes are GitHub-only as requested. Nothing in this update was deployed to Sites, and no audience or domain settings were changed. The existing private preview, if retained, still runs its older version. This application uses a Cloudflare Worker and **D1** for waiting-list storage; a static-only host will not save signups. Supabase is not needed for this waiting-list release.

1. Install the locked dependencies with `npm ci` (Node 22.13 or later). Configure your final HTTPS origin as `NEXT_PUBLIC_SITE_URL` in the build environment. This is also the canonical/sitemap/OG origin; do not launch with the example or old preview URL.
2. Create or select the production Cloudflare D1 database named `exclusive-apparel`, and set its real UUID as `D1_DATABASE_ID` in the build environment. The all-zero fallback in Vite is for local development only. Production binds this database as `DB`.
3. Keep **both** `NEXT_PUBLIC_STOREFRONT_MODE=waitlist` (build) and `STOREFRONT_MODE=waitlist` (Worker runtime). Keep `STORE_MODE=test`. The switches default to waiting-list mode; never set `store` to test a waiting-list launch. Keep customer auth disabled. Payment keys are not required. Resend must be configured for the automatic emails described below; without its key, signups remain saved and emails stay pending.
4. Run `npm run typecheck`, `npm test` and `npm run build`. The generated deployment configuration is `dist/server/wrangler.json`; it points to the Worker and `dist/client` static assets. Build-time D1 and launch configuration is included. The migration path is generated from the source `drizzle/` directory.
5. On your production D1 database, apply **all** unapplied migrations from `drizzle/`, in order. Through Wrangler: `npx wrangler d1 migrations apply exclusive-apparel --remote --config dist/server/wrangler.json`. `0007_waitlist-daily-budget.sql` adds the atomic daily email cap and provider pause controls. `0006_waitlist-emails.sql` adds surname, cellphone and the durable email queue without emailing existing records. The earlier `0005_launch-waitlist.sql` adds the signup table, unique email index and date index. `0004` retires the five unphotographed demo products while retaining order references. Back up an existing database before migration.
6. Deploy the build using your Cloudflare account (for example, `npx wrangler deploy --config dist/server/wrangler.json`). Configure a custom domain and HTTPS on that account. Never put credentials in tracked configuration.
7. Generate a unique management secret, for example `openssl rand -hex 32`. Store it as the **server-only** Worker secret `WAITLIST_ADMIN_SECRET`, using your host dashboard or `npx wrangler secret put WAITLIST_ADMIN_SECRET --config dist/server/wrangler.json`. It must contain at least 32 characters. Do not prefix it with `NEXT_PUBLIC_`, commit it, or share it with visitors. Open `/admin/` over HTTPS and enter this value as the management password. A new sign-in is required after an hour. Rotating the secret invalidates all existing management cookies.
8. Confirm a signup saves on your actual host, appears once in `/admin/`, and can be exported and removed. Check your custom domain, mobile layout, accessibility and browser console before public launch.

No R2 bucket is required for the bundled photographs or waiting list. If owner media uploads are enabled later, set `R2_BUCKET_NAME` before building and bind it as `BUCKET`. The previous commerce runtime will need additional payment, shipping, business and authentication setup before sales can open.

## Waiting-list behaviour

- `POST /api/waitlist` validates email, required first name and surname (100 characters each), required cellphone number (7–15 digits, up to 30 formatted characters), collection interest, optional valid product reference and explicit consent. Payloads are limited to 16 KiB and the request must have the same origin as the website.
- Emails are trimmed/lowercased. A unique database constraint and `ON CONFLICT DO NOTHING` keep concurrent/repeated signups to one record. Duplicates cannot overwrite someone else’s name, interest or consent. The same generic accepted response is used for new, existing and honeypot submissions.
- The record stores email, name, surname, cellphone, interest, product reference, consent version and creation date. Names/addresses are never written to application logs. Rate-limit keys use hashed IP/email values and expiry; raw IP addresses are not signup fields. The host may maintain its own operational logs.
- Signup requests are limited to 10 per IP per ten minutes and 3 per email per hour. Management sign-in allows 5 attempts per IP per fifteen minutes. These limits use the existing `rate_limits` table, not process memory. Cloudflare supplies the client IP; absent that header the limiter intentionally shares an anonymous bucket.
- Failed/missing database connections produce an error, never a success message. A successful form submission confirms database acceptance, not email delivery. New signups atomically save one email batch alongside the signup. No orders, stock reservations or accounts are created.
- `/admin/` is a dedicated waiting-list dashboard. Its API authenticates a signed, expiring HttpOnly/Secure/SameSite=Strict cookie. Forged owner headers and customer cookies do not grant access. The secret stays on the server; the form does not store it in local/session storage. Management requires HTTPS.
- The dashboard shows total signups, the last seven days, 50 records per page, the latest 100 contact/privacy messages and removal controls. CSV export includes **only the current page**, is private/no-store, quotes every field and neutralizes spreadsheet formulas. Handle exported personal data carefully and remove stale copies.
- Visitors can request correction/removal using `/contact/`. Review requests, verify through the email used to sign up, and remove the entry through the dashboard. Review the contact inbox regularly. Confirmation emails include contact/removal links and a Reply-To pointing to the owner inbox. Removal cascades to the queued message copy; it cannot recall an email already in flight or delivered. Delete inbox/export copies as appropriate. Any future launch mailing must provide an appropriate removal method.
- No selling prices, variant stock, buying controls or selling offers appear in the preview API/product presentation. Shipping rates and pricing sorts are hidden. Cart/checkout/account/order pages redirect to `/waitlist/`; their API entry points reject requests even if `STORE_MODE=live` or payment credentials are configured.

## Automatic waiting-list email setup

1. In Resend, add and verify **exclusive-apparel.co.za** using the DNS records Resend provides. The waiting-list sender is fixed to `Exclusive Apparel <noreply@exclusive-apparel.co.za>`; it is not the visitor's address. Domain verification, production credentials and real inbox delivery were not performed in this code update.
2. Add a sending API key as the server-only Worker secret: `npx wrangler secret put RESEND_API_KEY --config dist/server/wrangler.json`. Never commit the key or use a public environment variable. No Gmail password, Gmail forwarding rule or incoming-email webhook is needed.
3. Set `NEXT_PUBLIC_SITE_URL=https://exclusive-apparel.co.za` before building (or the actual final HTTPS site origin). The build copies this to the runtime `WAITLIST_SITE_URL` used for email links and `/email-logo.png`. Deploy that bundled PNG publicly. Email clients may block remote images until the recipient allows them; the brand and signature remain readable as text.
4. Apply migrations through `0007_waitlist-daily-budget.sql`, build, and deploy the Worker with its generated five-minute Cron Trigger. Confirm the trigger exists in Cloudflare. New signups attempt sending immediately after database acceptance via `waitUntil`. Cron retries due work, up to ten batches per invocation, and the authenticated dashboard has a **Retry due emails** button. This button respects the five-minute retry interval. Larger volumes require scaling the queue consumer and checking provider quotas.
5. Submit a new email address you control on the deployed site. Confirm one row in admin and two emails: the team notification at `1exclusiveapparel@gmail.com`, subject **Join Waiting List - Firstname Surname**, and the branded confirmation at the visitor's email. Check desktop/mobile email clients, reply routing, logo, spam folder and removal links. Repeat the signup and confirm it does not produce another pair of emails.

Both messages are submitted in one Resend batch after the signup is saved. Confirmation does **not** wait for Gmail receipt or someone opening the team notification. Customer confirmations include HTML and plain text, the website palette, a 112px logo and “Kind regards, Exclusive Apparel × T.s Industries.” Replies go to `1exclusiveapparel@gmail.com`. The team receives the fixed request message plus the submitted contact details and collection interest. The customer does not have to open an email app to join. These are signup confirmations; sending the eventual launch campaign is a separate action.

The queue stores a fixed message payload and an idempotency key per signup. Concurrent workers claim due jobs atomically. `submitted` means Resend acknowledged both messages, **not delivered to the inbox**; inspect delivery/bounce status in Resend. `pending` means not yet acknowledged. Missing API keys leave jobs pending without losing signups. Provider HTTP codes and generic timeout errors appear privately in admin; response bodies, addresses and credentials are not logged. Provider errors back off five minutes. Ambiguous/unresolved attempts stop after 23 hours and become `review`, because Resend's deduplication window is 24 hours. Check Resend before any manual resend; the dashboard does not blindly replay these records. Older `legacy` records are not emailed retroactively or overwritten by repeat submissions. Correcting existing details follows the verified contact/removal process.

References: [Resend batch API](https://resend.com/docs/api-reference/emails/send-batch-emails), [idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys), [domain verification](https://resend.com/docs/dashboard/domains/introduction).

## Daily sending budget and overflow

Resend Free allows 100 transactional emails per UTC day and 3,000 per month, including sent/received emails and each recipient. The requested owner notification plus customer confirmation costs **two emails per signup**, so the local limit permits **up to 50 signups/day**, not 100 confirmations plus 100 owner notifications. Every attempted batch reserves two slots, including retries and rejected requests, so failures can reduce that day's capacity. Signup storage has no 50-person daily cap. Overflow stays pending, in oldest-signup order, and is picked up by the five-minute scheduled sender on following days. Reset is midnight UTC / **02:00 South African time**.

The database trigger reserves allowance atomically with the job claim, so concurrent workers and the admin retry button cannot exceed 100 local recipient attempts per day. Deleting a signup does not refund allowance. Unsent queued entries keep `first_attempt=0`, so waiting several days does not expire them. The 23-hour ambiguity protection applies only after an actual attempt. Applying this migration to a database with earlier send attempts conservatively holds sending for the remainder of that UTC day, since earlier provider usage cannot be reconstructed reliably.

Provider daily/monthly quota errors pause this queue until the next UTC day, then retry; if the monthly allocation is still exhausted, it pauses again. This is a website-local cap, not a global account counter: other Resend projects and incoming Resend email can use allowance too. Use a dedicated Resend account for this site or leave appropriate capacity; the provider's quota remains authoritative. Existing commerce sending is blocked in waitlist mode. New signups remain saved during pauses. The admin dashboard shows reserved slots, pending signups and review cases. No launch marketing campaign is sent by this queue.
